# CP-H3 · One primary button per staff screen: audit

> Date: 31 October 2026 · v3.1 workstream W7 «Εμπιστοσύνη και απλότητα» · backlog item CP-H3
> Output: this audit and clickable mockups for the worst screens
> (`/mnt/project-files/milos/v31-mockups/w7-trust.html`, section H3). **No UI code changes** until ANR picks.

## 1. The rule (from the programming dialog, PR #147)

PR #147 redesigned the staff «Πρόγραμμα & προπόνηση» dialog (`aaf97997`). Its rule, applied to every staff screen:

1. **One filled (primary) button per screen state.** Its label says what happens
   («Ανάθεση», «Χρέωση 45 €», «Δημοσίευση»), never «OK» or «Υποβολή».
2. **Everything else is secondary**: outline, text link, or the «⋯» menu (`MoreMenu`).
   «Άκυρο» is always a text button.
3. **Rare options fold** under «Περισσότερα» / «Προχωρημένα» with a one-line summary of what is set (ADR-255).
4. **A disabled primary says why** (a line under it), instead of hiding.
5. **Selected state is not a primary.** A chosen chip or segment should not look like the filled
   button next to it (THEME.md: selected chips are Dojo; the proposal keeps Dojo but soft, see S1).
6. **Rows do not carry primaries.** In a list, the row opens a detail; per-row actions are
   secondary, or one bulk primary acts on the selection.

## 2. Method

- Every `page.tsx` under `apps/web/src/app/admin/**`, `app/platform/**`, `app/class-timer/**` and
  `app/events/hosting` (63 staff and console screens).
- For each page, the component tree it imports (4 levels, `components/ui` and nav excluded) was
  scanned for filled primary styles: `background: var(--primary)` / `bg-[var(--accent)]` with
  `--primary-contrast`, and the shared `primaryButtonStyle` (`components/staff/staff-ui.tsx`).
  The sign-in-expired dialog in `session-provider.tsx` was excluded (it shows on every page).
- The count is an **upper bound** (dialogs, tabs and conditional branches are counted together).
  Each screen in §4 was then read by hand to find what is visible **at the same time**.
- Script: kept outside the repo (helper only); numbers below are from commit `330eb707`.

## 5. The worst 8 (mockups with 2–3 alternatives each)

Picked by what is seen together and how often the screen is used: **Member profile**, **Staff home**,
**Finance (Εκκρεμότητες / Εταιρικοί)**, **Schedule + class popup**, **Settings**, **Shop orders**,
**Class timer control**, **Workout board**. Each has its mockup in the H3 section of
`v31-mockups/w7-trust.html` with a recommendation and open questions in Greek.

## 6. Order of work (after ANR picks)

1. S2 (SaveBar on settings pages): small, many screens, no decision needed. S1 once ANR agrees to the
   soft selected style (it touches THEME.md).
2. Member profile, Staff home, Class timer: the three with the most daily use.
3. Finance, Shop orders, Trials: the per-row primaries (S4).
4. A guard test like the existing `components/ui/*-guard.test.ts`: fail when a staff screen component
   renders more than one element with the primary style in its default state (rendered with
   testing-library, counting `data-primary` marks added to the shared button helpers).
